## Recommended architecture

Approved Bellback references -> Meshy candidate generation -> original GLB archive -> Blender source and refinement -> versioned FBX/textures -> Unreal candidate import -> game-camera and motion review -> packaged integration.

Two separate optional Meshy connections:

- **Meshy Blender Bridge:** website sends a completed model to the open Blender scene. Local HTTP on port 5324. No API key since plugin v0.6.0. Requires Pro or above according to official integration documentation.
- **Official Meshy MCP server:** lets Codex submit Meshy tasks, query status, list tasks and download results. Requires an API key via `MESHY_API_KEY`, a usable Node/npm runtime and explicit setup. It does not directly edit Blender geometry.

Existing **Codex Blender MCP** controls and inspects Blender through the project-configured loopback port 9876. Existing local scripts/commandlets and build tools handle Unreal; this guide does not claim an Unreal MCP is installed.

Blender is the editable production source once the generated asset has been imported and accepted for refinement. Edits in Blender do not automatically synchronize back to Meshy. A new Meshy generation is another candidate, not an update to production topology, weights or UVs.

## Set up the website-to-Blender connection

1. Download the current ZIP from [Meshy's official Blender integration page](https://www.meshy.ai/integrations/blender).
2. Keep the ZIP intact. In Blender use Edit > Preferences > Add-ons > menu > Install from Disk. Select and enable the add-on.
3. Open a separate candidate scene. The bridge imports into the current scene.
4. Press N in the 3D viewport, open Meshy, and click Run Bridge. Confirm Bridge ON.
5. In Meshy's signed-in workspace open a completed model and choose DCC Bridge > Send to Blender.
6. Check geometry and switch to Material Preview to inspect textures. Save a candidate `.blend`, then reopen it and verify image files resolve.
7. Verify Codex's existing Blender MCP sees those same imported objects.

The bridge imports GLB/ZIP, sets up materials and merges duplicate vertices. It removes its temporary downloads. Separately preserve the original export before editing. Manual fallback is download GLB and import using Blender's glTF importer. This is useful both for troubleshooting and preserving an untouched source.

Use the plugin's print-oriented repair tools selectively. Bellback's open cavity and intentionally separate body/equipment parts should not be altered merely to satisfy a generic printability check.

## Add Codex generation control

1. In [Meshy API settings](https://www.meshy.ai/settings/api), verify API access and create a named project key such as `WonderChessLocal`.
2. Enter the secret locally through a credential-backed launcher or a user environment variable named `MESHY_API_KEY`. Keep the key out of conversation messages, versioned files and command logs. The user environment is a local configuration mechanism, not an encrypted vault.
3. Provide Node/npm with a working `npx` command, or install a reviewed version of the official `@meshy-ai/meshy-mcp-server` package under project support and launch its real entry point. The current bundled Node executable alone does not establish npm availability.
4. Add a project-scoped server alongside the existing Blender entry. The following is an example **after npx is available**, not a verified current-PC command:

```toml
[mcp_servers.meshy]
command = "cmd.exe"
args = ["/d", "/c", "npx", "-y", "@meshy-ai/meshy-mcp-server"]
env_vars = ["MESHY_API_KEY"]
```

5. Restart Codex so it receives the environment variable and new MCP configuration. Verify tool discovery and a read-only account/task request before creating a job. For reproducible production, record/pin the server version that actually passes the connection test.
6. The future workflow submits a job once, records its ID, polls that ID, downloads the result and verifies local files. A slow job should not trigger duplicate paid submissions.

Meshy documents account-balance consumption for MCP/API generation. A subscription does not make every automated operation unmetered. Confirm the actual account balance and operation estimate before the first batch; costs vary by operation/model and website/API options can differ. Begin with one geometry candidate and an explicit credit ceiling. Review it before spending on more candidates or final texture generation.

## Bellback production handoffs

### A. Reference intake

Prepare consistent individual creature views from approved source material, with no labels, swatches, extra creatures or background clutter. Preserve original references. Any new reconstruction of a hidden side is a proposal, not automatically approved. Multi-image API supports one to four views; validate consistency before use.

### B. Generate and preserve

Use image-conditioned geometry as the starting experiment. Judge the full creature for silhouette and face; treat the bell/support as components we can reconstruct precisely. Save task ID, model/version, available settings, actual input hashes, returned GLB, textures, thumbnails, account usage and a review note. Do not invent random seeds that the provider did not expose.

Suggested new candidate layout under the existing asset folder (not yet created):

```text
inputs/meshy/r001/
  input-images/
  raw-model.glb
  textures/
  task.json
  provenance.json
stages/forms/meshy_r001/
  Bellback_forms.blend
  review/
```

### C. Blender refinement and review

Import to isolated collections, establish meter scale/+Y source forward, and compare against the approved 2.2 m crown and body envelopes. Inspect muzzle, eyelids, four toes, limb separation, branch handedness, hollow bell and support. Preserve raw geometry while reshaping a working copy. Repeat matched clay/current-game-camera views. The previous generation or a textured preview is not forms approval.

After accepted forms, build deformation topology and perform provisional crouch/stride/head-turn tests. Refine UVs, bakes, broad material/value groups, skin weights, export skeleton and animations. A new Meshy remesh after this point is a topology change requiring revalidation/rework of dependent data.

### D. Rigging choices

Meshy's current web guide offers Quadruped and Smart Rig modes. Its documented Rigging API remains limited to standard humanoids. A web-generated quadruped rig can be evaluated as a candidate; do not assume the MCP rigging tool supports that same mode. Bellback still requires a rigid main bell, bounded clapper behavior, proper foot contacts and motion fitted to game events. Blender is the final control point for these requirements.

### E. Unreal and package

Export the accepted candidate via the measured normalized FBX recipe, with separate mesh/rig and animation files as appropriate plus texture maps. First import under an isolated candidate location, verify skeleton/root scale/rest dimensions, material channels, contacts, bounds and LOD readability. Review at the current board camera. Integrate with the stable `wc_vn_bellback` identity only after required approvals and checks; preserve current proxies and prior evidence as rollback inputs. Existing combat code remains authoritative for effects and hit timing.

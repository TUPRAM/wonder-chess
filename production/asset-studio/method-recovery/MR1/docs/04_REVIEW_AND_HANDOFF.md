# 04 — Review, stop rules, fallback and handoff

## Keep the session focused
The previous report establishes working MCP/edit/save/capture behavior. Check the current connection, active file, unsaved changes, reference path and ability to receive one actual image. Repair a genuine failure. Do not spend the session re-verifying every already working service or adding a new orchestration framework.

Run focused source and geometry checks after edits. Reserve the unrelated repository-wide Python/specification suite for relevant code changes or the final integration check. More green tooling tests do not answer whether an eyelid wraps an eye.

## Baseline and candidate safety
Never overwrite r003 or its .blend1. Preserve the frozen checkpoint. Do not assume the uploaded .blend1 is the better baseline. Check newer local files and unsaved changes.

Use an explicit candidate collection plus render allowlist. The saved file contains failed experimental geometry; names and stored flags alone do not establish active view-layer visibility. Inspect `hide_viewport`, `hide_render`, collection exclusions, local-view state and relevant modifiers in Blender. Avoid mass unhide/select-all operations.

No armature or animation exists for this new study according to the report and saved inventory. Therefore preserving failed facial vertex indices for a nonexistent production skin is not a valid constraint. ## Fixed captures
Reuse `CAM_front`, `CAM_profile`, `CAM_three_quarter`, `CAM_face` and `CAM_back` only after checking current aim/framing. Add the opposite three-quarter and top view as review-only cameras if absent.

Record camera matrix, projection/lens, clipping, framing, resolution, material override, world, light transforms/strengths, exposure/view transform, and visibility allowlist. Keep them identical for each baseline/candidate comparison. A supplementary light-reversal comparison is allowed but must be applied to both.

Use existing review automation; do not replace it merely to increase test counts. Capture at a resolution with enough native pixels to inspect the eye region. Do not upscale a small viewport image and call it higher-detail evidence. Disable depth of field and glamour post-effects for the diagnostic pass. Make the entire relevant region visible; cropped-off defects cannot pass.

The illustration is a design reference, not a calibrated orthographic measurement. Compare intended shapes and landmarks under compatible views. Do not treat raw pixel similarity between a painted sheet and a differently posed render as a likeness score.

The first reviewer should inspect images before reading the modeler's explanation of why the method ought to work. A separate context/agent is useful when actually available; otherwise disclose self-review. Confirm that image pixels were returned and examined, not just that a screenshot path exists.

## Three different outcomes
- `METHOD_PROOF_ACCEPTED`: the narrow construction appears better and permits internal integration. Record limits.
- `READY_FOR_PRAM_REVIEW`: the complete contextual candidate is prepared, with open concerns disclosed.
- `REVISE` or `METHOD_BLOCKED`: critical forms still fail; no pipeline advancement.

Reference approval stays current unless the reference itself changes. Existing form rejection remains in history. New geometry never inherits a prior approval automatically.

## Effort control
The user authorizes this specific change of representation. Document it as the AS1 method review. Do not change the two-no-improvement rule globally.

For each of the two genuinely distinct proofs, permit an initial construction and up to two meaningful corrective passes that target a named defect. Stop earlier for a clear dead end. Renaming the task, moving from one array formula to an equivalent one or adding polygons is not a reset.

Give short result summaries after substantial visible changes. When Pram interacts with the desktop, yield control. Do not force focus, disable interruption protections or repeat keyboard events blindly. On a tool timeout, inspect state before repeating an operation.

## Focused intervention / replacement-base brief if the new method fails
Do not request 'make the whole hero AAA.' Prepare this narrowly scoped handoff:

> Correct one stylized eye/socket/cheek region and one primary hair sweep for the approved Ada reference. Supply an editable low-density cage or purposeful sculpt with matched front/profile/three-quarter images. Retain approved overall proportions and the current torso context; no rig, textures, Unreal integration or full-body production is requested. The proof must eliminate raised eye patches, cheek banding, unwrapped lids, tubular hair roots and temple pinching without losing Ada's calm expression or hairstyle.

Include source hash, exact objects, approved reference crops, critical defects, current measurements, failed methods and file formats. This brief can be used for a focused human modeling session or evaluation of an already-owned/approved base. The user has not authorized spending, downloading unknown assets or external model uploads.

If a suitable base is proposed, document provenance, license permission, topology, style fit, integration work and why it changes the failed capability. Ask for necessary approval before acquisition/use. Do not claim that a base or image-to-3D service guarantees a result.
